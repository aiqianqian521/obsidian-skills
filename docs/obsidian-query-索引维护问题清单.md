## 一、P1 重要（索引维护效率 / 自动化）

### 1. 全量重建慢且无增量更新
- **位置**：`build-index.mjs` L49（递归 `readdirSync` 全量扫描）、L132（全量 `writeFileSync`）
- **现象**：每次运行都扫描全部 vault（当前 317 篇，随库增长线性变慢），耗时 ~120s。
- **影响**：无法做到"每次保存/新增即重建"；频繁触发会持续阻塞 2 分钟。
- **根因**：索引设计为全量 TF-IDF，无增量/无 mtime 差量逻辑。

### 2. 无自动触发机制（新增文件后需手动跑）
- **位置**：无 watch/定时逻辑；SKILL.md 仅写"significant changes 后 re-run"
- **现象**：新增/移动/改名任一 .md 后，全文索引不包含它，需人工或 agent 手动重建才可搜到。
- **影响**：新归档内容"查不到"，容易遗漏；本轮归档 8-31 就曾因索引停在 08-27 导致新文件全文搜不到。
- **根因**：build-index 是 CLI 一次性工具，无监听、无 hook、无增量；Obsidian 自身无官方 CLI 触发外部进程。

### 3. 方案取舍未定（需后续拍板）
针对"新增后自动重建"，已评估：
- **A. 常驻文件监听 watcher**（Node/PowerShell 防抖监听 vault 变更→触发重建）
  - 优点：真正"新增后自动"
  - 代价：需常驻进程/自启/崩溃恢复；重建 ~2min 窗口内新文件暂不可全文搜；占用资源
- **B. 固化进归档/写库流程 + 一键脚本（倾向推荐）**
  - 优点：零常驻、按需重建、可靠（agent 写库与重建同流程）
  - 代价：依赖流程执行，非纯自动
- **C. 插件侧触发（Templater/Bases）**：受沙箱限制无法 shell 调 node + 全量重建过重 → 不推荐

### 4. 无"一键重建"脚本封装
- **现象**：重建命令冗长、无跨平台便捷入口（.ps1/.bat），手动执行易出错/遗忘。
- **建议**：封装 `rebuild-search-index.ps1`（含 vault 路径默认值），双击或一行调用。
